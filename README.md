재고 품절(OOS) 데이터 기반 상품·매장 운영 이슈 분석 포트폴리오

---

## 📌 프로젝트 개요

리테일 운영 환경에서 상품이 **안 팔리는 이유**는 단순하지 않습니다.  
실제로는  
- 수요가 없어서 안 팔리는 경우도 있고  
- 재고 부족(품절) 때문에 팔리지 못하는 경우도 존재합니다.

본 프로젝트는 **재고 품절(Out-of-Stock, OOS) 데이터**를 기반으로  
> “이 상품이 안 팔리는 이유가 수요 부족인지, 재고/운영 문제인지”  
를 **데이터로 구분**하고,  
운영 관점에서 바로 활용 가능한 분석 결과를 도출하는 것을 목표로 합니다.

---

### 데이터 그레인(Grain)
- **상품 × 매장 × 옵션(l2) × 일자** 단위 재고 상태를 기록하는 로그 데이터

### 핵심 엔티티/키 정의
- 상품: `e_code`
- 옵션(사이즈/변형): `l2_id`
- 매장: `store_id`
- 수집 시각/일자: `collected_at`(또는 date)
- 재고 수량: `qty`

### 데이터 흐름(Lineage)
`Uniqlo API/페이지(JSON) → 수집 파이프라인(Python) → MySQL 로그 적재 → 지표/집계 생성 → 산점도/히트맵/Top 리스트 산출물`
---

## ⭐ STAR 기반 프로젝트 설명

### 상황

리테일 매장 운영 경험 및 데이터 분석 관점에서,  
다음과 같은 문제를 발견했습니다.

- 동일한 상품임에도 매장별 판매 성과가 크게 다름
- 단순 매출/판매량만으로는  
  → **수요 문제인지, 재고 부족 문제인지 구분 불가**
- 운영 실무에서는 “어떤 상품부터 조치해야 하는지” 판단 기준이 부족

👉 **품절(OOS) 데이터를 활용한 구조적인 진단 프레임워크**가 필요하다고 판단했습니다.

---

### 과제

다음 목표를 설정했습니다.

- 전체 상품을 **동일한 기준**에서 비교 가능한 분석 구조 설계
- 품절을 단일 수치가 아닌 **패턴 관점**에서 해석
- 상품 문제 / 매장 운영 문제를 **의사결정 관점에서 분리**
- 분석 결과를 **PPT·리포트로 바로 활용 가능한 형태**로 정리

---

### 행동

#### 1️⃣ 데이터 수집·적재 파이프라인 구축
- **Python + Requests / Playwright**를 활용해 상품·매장 재고 데이터 수집
- Uniqlo API / 페이지 JSON 구조 변화에 대응하기 위해 **DFS 기반 파싱 로직** 구현
- MySQL 기반 스키마 설계 및 로그 적재
  - 상품 × 매장 × 변형(l2) × 일자 단위 재고 상태 기록
 
## ✅ Data Quality: 스키마 검증 & 정합성 검증 자동화(운영 관점)

외부 API 기반 수집은 응답 구조 변경, 필드 누락, 비정상 값(예: 음수 재고) 등으로 인해  
분석 결과를 왜곡할 수 있어 **수집→적재 전→적재 후** 단계에 걸친 검증 프로세스를 운영 관점으로 설계했습니다.

### (A) 수집 단계 검증
- 요청 실패/타임아웃/빈 응답을 감지하고, 재시도(Retry) 및 에러 로그로 추적 가능하도록 구성

### (B) 적재 전 스키마 검증
- 필수 필드 존재 여부, 데이터 타입, NULL 규칙을 기준으로 검증
- 검증 실패 레코드는 별도 로그로 격리하여 오염 데이터의 유입을 차단

### (C) 적재 후 정합성 검증
- 중복키, 범위 위반(qty < 0), 레코드 카운트 급감 등 품질 이슈를 점검
- 문제 발생 시 “전체 재실행”이 아니라 **문제 실행(run)만 재처리**할 수 있는 흐름을 고려

#### 2️⃣ 핵심 품절 지표 정의
- 평균 품절 비율 (Mean OOS Rate)
- 매장 간 품절 편차 (Standard Deviation)
- 하루 종일 품절 여부 (`oos_rate == 1`)
- 연속 ‘하루종일 품절’ 기간(Persistence)

#### 3️⃣ 전체 상품 패턴 조망 (Scatter Analysis)
- **산점도 분석**
  - X축: 평균 품절 비율
  - Y축: 매장 간 편차
- 모든 상품을 동일 기준으로 시각화하여 **품절 유형 분류 가능**하게 설계

#### 4️⃣ 의사결정 중심 사분면 분류
- **Q1**: 자주 품절 + 매장별 편차 큼  
  → 배분/운영 이슈 가능성
- **Q4**: 자주 품절 + 매장별 편차 작음  
  → 구조적 공급 부족 가능성
  ![전체 상품 품절 패턴 산점도](out/scatter_products.png)

#### 5️⃣ 원인 구체화를 위한 히트맵 분석
- 대표 상품을 선정해 **매장 × 사이즈 단위 품절 히트맵** 시각화
- 특정 매장 집중 문제 vs 전사 공통 문제를 직관적으로 확인

### 결과

- 단순 품절률이 아닌 **패턴 기반 품절 분석 프레임워크 구축**
- 상품을 다음과 같이 명확히 구분 가능
  - 배분/운영 개선 대상 상품
  - 구조적 공급 부족 상품
- 분석 결과를
  - 산점도
  - 히트맵
  - Top 문제 상품 차트  
  형태로 자동 생성하여 **PPT·보고서 바로 활용 가능**
- “분석 → 해석 → 운영 액션”으로 이어지는 구조를 명확히 제시

## 📈 Data Quality Metrics (품질 지표)

파이프라인/데이터 상태를 “감”이 아니라 수치로 모니터링하기 위해 다음 지표를 정의했습니다.

- **API 실패율(API Failure Rate)** = 실패 호출 수 / 총 호출 수  
- **빈 응답률(Empty Response Rate)** = 빈 응답 수 / 성공 응답 수  
- **스키마 위반율(Schema Violation Rate)** = 스키마 검증 실패 레코드 수 / 총 레코드 수  
- **중복률(Duplicate Key Rate)** = 중복 복합키 레코드 수 / 총 레코드 수  
- **핵심 필드 NULL 비율(Key Field Null Rate)** = (예: e_code 또는 qty가 NULL인 레코드 수) / 총 레코드 수  
- **데이터 신선도(Freshness/Latency)** = 적재 시각 - collected_at
